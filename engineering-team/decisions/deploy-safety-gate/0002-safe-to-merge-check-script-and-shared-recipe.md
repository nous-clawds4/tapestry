# ADR 0002: Safe-to-merge check — committed script as mechanism, one shared doc as the canonical recipe

**Status:** Proposed
**Date:** 2026-07-18
**Story:** `engineering-team/stories/deploy-safety-gate/2-cycle-safe-to-merge-check.md`

## Context

Story #1 shipped `GET /api/deploy-safety/status` (ADR 0001): one unauthenticated GET returning `safeToDeploy` (boolean), `verdict`, `reasons[]`, `checkedAt`, `bufferMs`, and per-source detail. Nothing consumes it pre-merge. This story wires the answer into every deploy-triggering promotion. The acceptance criteria, quoted for the record:

- **AC-1 (check before merge, on the instance that merge redeploys):** "Given a cycle-staging or cycle-prod run has a change ready to merge, when the procedure reaches the deploy-triggering merge, then as that merge's immediate precursor it obtains the deploy-safety status answer shipped by story #1 **from the instance this specific merge will redeploy** … and it merges only on a safe verdict just observed — a safe answer is acted on, not banked across an open-ended delay. The procedure consumes the verdict as delivered; it does not re-derive its own safety policy from raw schedule data."
- **AC-2 (unsafe → bounded, journaled wait-and-recheck; never merge on unsafe):** "…it waits and rechecks on a stated cadence up to a stated bound — both written into the recipe, not improvised per run — and every attempt is visibly recorded in the run's record: when the check was made, what the verdict was, and, when unsafe, the reason the answer gave. At no point does the procedure merge while the most recently observed verdict is unsafe, and at no point does it wait without recording that it is waiting."
- **AC-3 (bound exhausted or no usable answer → loud stop, operator decides):** "…the procedure stops without merging, reports the last observed state and why it stopped, and hands the decision to the operator. An answer that could not be obtained is never treated as safe… 'Merged anyway without saying so' and 'hung with no output' are both defects."
- **AC-4 (cycle-full inherits by delegation):** "…each deploy-triggering merge it makes is protected by the same check because cycle-full delegates to the underlying cycle procedures — it carries no check logic or recipe text of its own, and no path through cycle-full reaches a deploy-triggering merge without the check."
- **AC-5 (one canonical recipe; `feat/tags` explicitly covered):** "The check recipe exists in exactly **one** shared document, following the same update-once-inherit-everywhere pattern the smoke-test recipe uses… The document explicitly covers promotions to `feat/tags` → tags.brainstorm.world."

Ratified product decisions (not relitigated here): wait-and-recheck rather than abort or a fixed look-ahead; the verdict policy lives entirely in the story #1 answer; one canonical shared doc on the SMOKE_TEST.md pattern; tags coverage via that doc. The book's pre-registration delegates to this phase: "How the cycle-skill check is made testable (e.g., a shared script the skills invoke vs a prose recipe), and the wait-and-recheck bounds (attempts × interval)" (book §Open design decisions, item 4). The story additionally delegates the shared document's location, whether the recipe pins `?bufferMinutes=` (ADR 0001 Consequences flag), and the journaling medium.

## Options considered

### Option A — Committed check script as the mechanism + one shared doc as the canonical recipe (chosen)

A new executable, `scripts/check-safe-to-merge.sh <instance-base-url> [max-attempts] [interval-seconds]`, owns the loop: fetch → journal → branch on `safeToDeploy` → sleep → repeat, with distinct exit codes for safe / bound-exhausted / no-usable-answer / usage-error. A new shared doc, `docs/SAFE_TO_MERGE.md` (sibling and pattern-twin of `docs/SMOKE_TEST.md`), is the canonical recipe: it names the script as *the* way to run the check, pins the numbers, maps branch → instance → consumer (including `feat/tags` → tags.brainstorm.world), and states the verdict-handling rules (exit 0 → merge immediately; anything else → stop, show the journal, operator decides). The three cycle skills reference the doc exactly the way they reference SMOKE_TEST.md; none restates the numbers.

Pros: AC-2's "not improvised per run" is enforced by construction — the cadence, bound, journal format, and the tricky failure semantics (fetch failure ≠ unsafe ≠ safe; never exit 0 on a last-observed-unsafe) are written once in tested code, not re-typed per run from prose; the script is a directly testable surface (spawn it against a stub HTTP server, assert exit codes and journal lines — `harness-lint.test.js` precedent), which Direction-mode's failing-tests-first constraint needs; a manual `feat/tags` promotion runs the *identical* mechanism with a different URL, so tags coverage is one table row, not a parallel procedure; the doc stays the single canonical recipe (AC-5) while the script keeps it honest.
Cons: two artifacts to keep aligned (mitigated: the doc contains no loop logic to drift — it names the script and the numbers, and a doc-content test asserts the numbers match the script's defaults); a new committed script to maintain.

### Option B — Pure prose recipe with an embedded snippet (SMOKE_TEST.md-style, no script)

The shared doc carries a bash `until`-loop snippet (as SMOKE_TEST.md Tier 1 does) that each run copy-executes.

Pros: one artifact; exactly mirrors the established pattern; no new executable. Cons: SMOKE_TEST's Tier-1 snippet is a benign poll where an improvised variant costs nothing; *this* loop is a safety gate where the subtle branches are load-bearing — treating a curl failure as safe, forgetting the journal line, or "improving" the cadence mid-run are precisely the defects AC-2/AC-3 name, and a copy-typed snippet re-opens all of them every run. Testability drops to doc-content assertions only (prose can be asserted present, not correct). Rejected: the mechanism belongs in code once; prose is the right form for the *policy around* the mechanism, and Option A keeps that prose canonical.

### Option C — Each skill carries its own inline check steps

Write the loop into cycle-staging and cycle-prod directly; describe the tags variant in OPERATIONS.md.

Rejected outright: three restatements of one recipe violates AC-5 verbatim ("exists in exactly one shared document"), recreates the drift the smoke-test pattern was built to end, and leaves `feat/tags` covered by a fourth, different text.

### Option D (placement alternative) — Gate at PR-open instead of pre-merge

Run the check at the top of the cycle (before or at PR creation), so an unsafe instance stops the run before any artifact exists.

Rejected: PR creation → merge is separated by review/approval time that is open-ended by design (cycle-prod's step 3 waits for a human); a safe verdict observed at PR-open is exactly the "banked" answer AC-1 forbids. The check must be the merge's immediate precursor. (Named because it is the intuitive "fail fast" placement an implementer might reach for.)

## Sub-decisions (delegated to this ADR by the story / book)

1. **The numbers: cadence 60 s × bound 45 attempts (≈ 45 minutes), script defaults = recipe canon.**
   - *Cadence 60 s:* the check is one cheap GET; 60 s bounds the merge-latency after the window opens to ≤ 1 minute, keeps the worst-case journal at 45 readable lines, and matches the granularity of the transients it rides out (legacy 30 s clear-poll, ~30 s BullMQ stall interval) — polling faster mostly re-observes those. Alternative — exponential backoff — rejected: saves nothing that matters (requests are trivial) and costs prompt merge-after-clear plus journal regularity.
   - *Bound 45 attempts:* sized to absorb the worst *common* case — a fire that lands inside the 10-minute buffer window (up to 10 min of `NEXT_FIRE_WITHIN_BUFFER`) followed by a default-profile task run (30-minute registry default kill-timeout, ADR 0025) plus ~5 min slack for the post-deploy stalled-active transient and the legacy 30 s clear lag: 10 + 30 + 5. It deliberately does **not** try to outlast the 4 h/6 h override tasks (`updateAllScoresForOwner`, `processAllTasks`): for those the bound exhausts into AC-3's loud stop with the journal naming the running task, and the operator decides — that is the designed behavior, not a failure of the bound. Alternatives — 15 minutes (rejected: exhausts mid-run for any default-timeout task caught in flight, converting the *common* case into operator interrupts, which the wait-and-recheck design exists to absorb); unbounded with operator Ctrl-C (rejected: AC-2 requires a stated bound; "hung politely forever" is AC-3's named defect).
   - *No-usable-answer fast path:* 3 **consecutive** unusable attempts (connection failure, non-2xx, unparseable body, missing `safeToDeploy`) → exit early with the no-answer code (~3 min on a dead instance, not 45). A usable answer resets the counter. Rationale: AC-3 treats "cannot be obtained at all" as its own stop condition — burning the full bound on a down instance delays the operator's decision for no information gain, while a single blip shouldn't kill a run.
   - *Staleness rule (AC-1's "just observed"):* the merge must be the immediate next action after exit 0. If more than **5 minutes** elapse between exit 0 and the merge command, re-run the check. Ground: a safe verdict guarantees ≥ 10 minutes to the next fire; 5 minutes spends at most half that margin, and the merge+workflow-trigger itself takes seconds.
   - *Overrides:* `[max-attempts] [interval-seconds]` args exist for two callers only — the test suite (small numbers for speed) and an operator's explicit post-stop decision to wait longer (journaled, per AC-3). The recipe states the defaults as the canonical numbers; a cycle run never passes overrides on its own initiative.
2. **`?bufferMinutes=` is NOT pinned — the recipe uses the instance default, and journals the echoed `bufferMs`.** Ratified decision 1 says the *instance* owns the verdict policy and consumers do not relitigate it; a caller-pinned `?bufferMinutes=10` would freeze today's policy in the recipe and silently override any future instance-side policy change — the wrong ownership direction. The response echoes effective `bufferMs`, and the journal captures every response, so the window each check actually used is always in the run record; divergent-window drift is visible rather than possible-but-hidden. This satisfies ADR 0001's Consequences flag by *stating the chosen value*: the instance default, explicitly. Alternative — pin `?bufferMinutes=10` in the recipe — rejected as above (also: a typo'd param 400s, adding a failure mode for zero benefit).
3. **Slots.** *cycle-staging:* new step **4 "Safe-to-merge check"** between "3. Open PR" and the merge (merge and later steps renumber 5–9) — target `https://staging.brainstorm.world`. *cycle-prod:* new step **4 "Safe-to-merge check"** between "3. Wait for explicit user approval" and the merge (renumber 5–8) — target `https://tapestry.brainstorm.world`. The order is approval **then** check, never the reverse: a safe verdict obtained before an open-ended human approval wait is the banked answer AC-1 forbids. **The approval stands across the bounded wait** — stated explicitly in the skill: the operator's step-3 approval covers *what ships* (the bundle, fixed at PR-open), which the wait does not change; a bounded ≤ 45-minute journaled wait between approval and merge is consistent with AC-1 because the *safety* answer — the thing that must be fresh — is re-observed at the end of the wait, immediately before the merge. If the check stops instead (AC-3), the hand-back to the operator is a fresh decision; the old approval is not silently reused as permission to proceed-on-unsafe.
4. **cycle-full: delegation verified, two navigation lines + one halt entry added, no recipe content.** AC-4's claim holds at the top ("Each individual skill defines the work for its stage") but *not* structurally today: the inline Stage 2/Stage 4 step summaries are a path an agent can follow to the merge without ever seeing the check. Fix without violating "no check logic or recipe text of its own": add one summary line to each stage list — Stage 2, between items 3 and 4: "Safe-to-merge check (delegated to cycle-staging — the merge's immediate precursor)"; Stage 4, between items 2 and 3: "Safe-to-merge check (delegated to cycle-prod — the merge's immediate precursor)" — and one entry in Halt-on-failure semantics: "Safe-to-merge check stops (bound exhausted while unsafe, or no usable answer)". cycle-full names the step and the delegate; it carries **no** URL, no numbers, no script name, no doc link — a content test can assert `cycle-full/SKILL.md` contains neither `check-safe-to-merge.sh` nor `SAFE_TO_MERGE.md`, making AC-4 structurally testable. Alternative — zero edits to cycle-full, relying on the existing delegation sentence — rejected: the inline summaries are what a running agent actually follows; leaving the check absent from them leaves AC-4's "no path" clause aspirational.
5. **`feat/tags` coverage: a dedicated section of the shared doc, same mechanism, different URL.** `docs/SAFE_TO_MERGE.md` carries a branch → instance → consumer table (`staging` → staging.brainstorm.world → cycle-staging; `main` → tapestry.brainstorm.world → cycle-prod; `feat/tags` → tags.brainstorm.world → *manual promotion, this section*) and a short "Manual promotions to `feat/tags`" section: run `scripts/check-safe-to-merge.sh https://tags.brainstorm.world` as the immediate precursor of the merge into `feat/tags`, same exit-code handling, same journaling (paste the output into wherever the promotion is being recorded — PR body or session report). The doc also notes the transition reality: an instance whose branch predates story #1 404s the endpoint — that is "no usable answer" (exit 2), never safe; promote the endpoint to that branch first or make an explicit recorded operator decision. Other deploy-triggering sandbox branches (`feat/communities`, `feature-magic-carpet`, `feat/curate`) may adopt the same row-and-URL pattern later; out of this story's scope per the story.
6. **Parsing: no `jq` requirement — POSIX-tool extraction of the two load-bearing fields, raw JSON journaled verbatim.** ADR 0001 sketched `jq -e '.safeToDeploy'` as the calling convention; this ADR keeps the *contract* (machine-checkable boolean, exit code = verdict) but moves it to the script boundary instead of a `jq` boundary: nothing in `scripts/` or the skills uses `jq` today, it is not in macOS's default toolset, and the check must not die on a missing formatter at the exact moment it matters. The script extracts `safeToDeploy` (and `reasons` for the journal line) with `grep`/`sed` against the pinned compact-JSON contract (field renames are already declared breaking changes in ADR 0001's Consequences), and appends the **raw response body** to every journal line — so control flow needs only one boolean, and full fidelity survives any parser limitation. A response where `safeToDeploy` cannot be extracted as `true`/`false` is an *unusable answer* (counts toward the 3-strike exit), never safe. Not a supersession of 0001 — its payload contract is unchanged; only its illustrative consumer sketch is refined.
7. **Journal medium: script stdout, captured into the run's record.** One line per attempt — `[<UTC ISO timestamp>] attempt <i>/<N> verdict=<safe|unsafe|no-answer> reasons=<[...]|n/a> raw=<response body or curl error>` — plus a final line stating the outcome and why. The skills require the check's full output to be included in the run's report (cycle-staging step "Report", cycle-prod step "Report"); under Direction mode the journal entry carries it, satisfying the book's own safe-window evidence bullet (6c). AC-2's when/what/why maps to timestamp/verdict/reasons per line; "hung with no output" is structurally impossible because every attempt prints before it sleeps. Alternative — a journal file under `/tmp` or the repo — rejected: a file adds cleanup/gitignore questions and hides the wait from the live session, which is the *opposite* of "visibly recorded."
8. **Doc location and name: `docs/SAFE_TO_MERGE.md`.** Sibling of the pattern it copies (`docs/SMOKE_TEST.md`), named for the operator-facing action (the story's own vocabulary: "safe-to-merge check"). Neither the doc nor the script is added to `scripts/harness-def-paths.txt`, following the SMOKE_TEST precedent (ops recipes are consumed by the harness, not part of its definition); revisit only if the def-paths convention is ever widened to ops recipes — in which case SMOKE_TEST.md and this pair go in together.
9. **Lint compliance by construction:** public https URLs in the skills are L5-clean (verified against the actual grep — only `localhost:<digits>` trips it); the script and doc carry no machine-local absolute paths (L6; invocation is repo-relative `scripts/check-safe-to-merge.sh`); skill links to the doc use the resolving relative form `../../../docs/SAFE_TO_MERGE.md` (L8); the implementation commit touches `.claude/skills/**` → it must also add an `engineering-team/CHANGELOG.md` row (L10); no capped file changes (L11).

## Decision

We chose **Option A** — a committed `scripts/check-safe-to-merge.sh` owning the wait-and-recheck mechanism (60 s cadence × 45 attempts, 3-strike no-answer fast exit, distinct exit codes, per-attempt stdout journal), and one canonical `docs/SAFE_TO_MERGE.md` that names the script, pins the numbers, maps every covered branch → instance (staging, main, and `feat/tags` → tags.brainstorm.world), and states the verdict-handling and staleness rules. cycle-staging and cycle-prod gain one referencing step each as the merge's immediate precursor (post-approval in cycle-prod, approval-stands stated); cycle-full gains only delegation-naming lines and a halt entry. It is the only option that makes AC-2's non-improvisation and AC-3's failure semantics properties of tested code rather than of per-run transcription, while keeping AC-5's single canonical recipe and giving Direction-mode's failing-tests-first a real surface (script behavior tests + doc/skill content assertions, both with in-repo precedent).

## Consequences

- **Enables:** the gate actually guards — every cycle promotion and any manual `feat/tags` promotion runs the same checked mechanism; the operator's disable-everything-before-promoting mitigation (in effect since June) can be retired; the book's own staging merges get their bullet-6c evidence from the same journal output; future sandbox branches are covered by adding one table row.
- **Constrains:** the script's exit-code contract (0 safe / 1 bound-exhausted-unsafe / 2 no-usable-answer / 3 usage-or-environment-error) becomes consumed by three skills and the doc — changing it is a breaking change to the promotion procedures; the endpoint payload contract from ADR 0001 hardens further (the script greps `safeToDeploy` and `reasons` — renames now break ops tooling, as 0001 predicted); cycle skill step numbering shifts (steps after the insertion renumber), so external references to "cycle-staging step 4" become stale.
- **Sequencing reality (accepted):** production and tags instances serve the endpoint only after story #1's code is promoted to `main` / `feat/tags`. Until then, a cycle-prod or tags check exits 2 (no usable answer → loud stop, operator decides) — which is correct fail-closed behavior, not a defect; the doc says so. The first prod promotion carrying this very story will itself hit that stop and proceed as an explicit recorded operator decision.
- **New debt / follow-ups:**
  - "Proceed anyway after a stop" is procedural (the skill requires an explicit, recorded operator decision) — nothing mechanically prevents a merge after exit 1/2. CI-side enforcement is explicitly out of scope at intake; if procedure proves insufficient, that is the escalation path.
  - The doc↔script number alignment (45 × 60) is held by a content test, not a single source; if either changes without the other the test fails — acceptable coupling, but note it in the test plan.
  - Neither artifact is in `harness-def-paths.txt` (sub-decision 8); if the convention widens to ops recipes, add SMOKE_TEST.md, SAFE_TO_MERGE.md, and the script together.
  - `cycle-local` is untouched: a local rebuild kills local in-flight tasks, but it is not a deploy-triggering *merge* and is outside frame bullet 4's coverage; a future story could point cycle-local at `localhost:$TAPESTRY_PORT` with the same script.
- **Firmware reinstall required?** **No** — no concept definitions are added or changed (verified live against the Concept Graph, 48 concepts, none in this domain).
- **New dependencies:** none (bash + curl + coreutils; deliberately no `jq`). **New lint/build tooling:** none.

## Implementation notes

Test-file changes this ADR implies (the new script/doc suites, runner registration) belong to Phase 3 — the Tester's lane — never to implementation (template rule; Direction-mode Gate 4 pins an empty `test/` diff after Gate 3).

- **File: `scripts/check-safe-to-merge.sh` (new, executable, `#!/usr/bin/env bash`, `set -uo pipefail`).**
  - Interface: `check-safe-to-merge.sh <instance-base-url> [max-attempts] [interval-seconds]`; defaults `45` and `60`. Missing/malformed URL arg → usage to stderr, **exit 3**.
  - Loop, per attempt `i` of `N`: `body=$(curl -sf --max-time 10 "$BASE/api/deploy-safety/status")`; on curl failure journal `verdict=no-answer raw=<curl exit + note>`, increment the consecutive-unusable counter; on success extract `safeToDeploy` with a tolerant compact/spaced-JSON pattern (e.g. `grep -oE '"safeToDeploy"[[:space:]]*:[[:space:]]*(true|false)'`) and `reasons` (e.g. `grep -oE '"reasons"[[:space:]]*:[[:space:]]*\[[^]]*\]'`); unextractable boolean → unusable (counts toward the 3-strike), never safe.
  - `true` → journal the attempt, print `SAFE — merge may proceed (act immediately; re-run if >5 min elapse)`, **exit 0** at once (no residual sleep). `false` → journal with `reasons`, reset the unusable counter, sleep `interval` unless `i == N`. Counter hits 3 → final line `NO USABLE ANSWER — not treated as safe; operator decides`, **exit 2**. Loop exhausts → final line `BOUND EXHAUSTED (N×interval) — last verdict unsafe; operator decides`, **exit 1**.
  - Journal line format per sub-decision 7; timestamps via `date -u +%Y-%m-%dT%H:%M:%SZ` (portable GNU/BSD).
  - The script branches **only** on `safeToDeploy`. It must not branch on `reasons`, `nextFire`, or any schedule content (journaling them verbatim is required; interpreting them is AC-1's forbidden re-derivation). Leave a comment saying exactly that.
- **File: `docs/SAFE_TO_MERGE.md` (new).** SMOKE_TEST.md-style header (audience: agents running cycles + human operators; purpose: single canonical definition of the pre-merge deploy-safety check; "Last updated:" line). Sections: what the check is + endpoint pointer (`/api/deploy-safety/status`, ADR 0001 payload); the canonical invocation (the script, the default numbers **45 attempts × 60 s** and their one-paragraph rationale, the 3-strike no-answer exit, the 5-minute staleness rule); the branch → instance → consumer table (all three public https URLs — `docs/` is lint-exempt and the skills already carry these hosts); verdict handling (exit-code table; exit 0 → merge immediately; exit 1/2 → stop, surface full journal, operator decides; proceeding after a stop is only ever an explicit recorded operator decision); buffer policy (instance default, no `?bufferMinutes=`, `bufferMs` journaled — sub-decision 2 rationale in two sentences); "Manual promotions to `feat/tags`" (sub-decision 5, including the endpoint-404 transition note); limits (endpoint must exist on the target; other sandbox branches optional adopters).
- **File: `.claude/skills/cycle-staging/SKILL.md`.** Insert new step 4 "Safe-to-merge check" after step 3 (Open PR); renumber current 4–8 → 5–9. Content: run the check as defined in [`docs/SAFE_TO_MERGE.md`](../../../docs/SAFE_TO_MERGE.md) against `https://staging.brainstorm.world` — the merge's immediate precursor; exit 0 → merge immediately (next step); any other exit → stop, include the full check output in the report, hand the decision to the user; proceeding on non-zero exit only as the user's explicit recorded decision. No cadence/bound numbers in the skill. Add an Error-handling bullet ("Safe-to-merge check exits 1/2: …") and the doc to §Reference.
