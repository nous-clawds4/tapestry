# ADR 0005: A new append-only Work Record concept (runtime-created, never mutated); two gated/serialized producers (`worked` + a session-attributed `noted` capture); produced resources referenced by locator and resolved at read; the goal-detail `records` array populated; and a bounded, corpus-independent `GET /api/brain/orient`

**Status:** Accepted
**Date:** 2026-07-23
**Story:** `engineering-team/stories/second-brain/5-sessions-read-the-brain.md`
**Builds on:** second-brain ADR 0004 — this story is the **first producer** of the record section ADR 0004 d10 built and left live-empty (`handleGetGoalDetail` returns `records: []` today, `src/api/brain/index.js:206`). It reuses ADR 0004's runtime-created-concept pattern (`ensureResourceConcept` → `ensureWorkRecordConcept`), the pure-core + read-time-derivation precedent (`resources.js` → `work-records.js`), the record-based linkage idiom (d2), the gated/validated/serialized write pattern (d6/d9), and the `create-resource` **core** (its mutex lives at the handler, so the core composes without nesting). ADRs 0001 (capture contract; adopt element machinery; derived-not-stored standing; read seam), 0002 (read-only brain module), 0003 (validated goal writes; `serializeGoalWrite`; the d8 save-schema fold) all remain binding.

## Context

The story (`5-sessions-read-the-brain`, gate-approved 2026-07-23). Acceptance criteria, quoted to confirm:

- **AC1** — bounded, corpus-independent orientation: a fresh session states which goals exist and identifies the one it serves from a **bounded** read whose cost does not grow with the number of goals; the served goal's deliverable/boundary come back verbatim.
- **AC2** — the session's output names the goal it served, and the record lives **in the brain, attached to that goal** (PRD §7.1; a scheduler-side log is a defect).
- **AC3** — a **work record** appears on the goal's spine: the session, a one-sentence standing summary, produced resources **as pointer cards**, and **≤2** plain-English questions; type word `worked`, dated, **no edit affordance**.
- **AC4** — work records are dated, attributed, **append-only** (never edited/deleted; a correction or a second session is a new entry).
- **AC5** — a session-born goal idea is a **capture attributed to the session** (dated; origin = the session) that **launches nothing**; proposal-queue treatment is story 6.
- **AC6** — writes gated (owner/loopback) + local-only + no new UI form; the brain read module stays read-only.
- **AC7** — copy discipline; the no-edit contract holds with live entries; sibling suites still pass; **and this story dispositions the `GoalDetail.jsx` findings** (OPEN.md row 86(b) + row 87 a/b/c).

Facts established at architecture recon (live instance + source, 2026-07-23; TA `11f23fe4…` runtime-resolved throughout; three-call concept-graph orientation run before source):

- **Work Record does not exist on the graph.** `GET /api/concept-graph/summaries` → 51 concepts, **0** work-record/session hits (the only `goal`/`work`/`record` matches are the infra graphs `concept-graph`/`core-nodes-graph`/`property-tree-graph`). Story 5 populates it. The design guide requires **work entries list produced pointers as pointer cards** — `PointerCard` (`GoalDetail.jsx:43-65`) is the reusable component.
- **The read module reads the whole corpus.** `readResolvedGoals` (`src/api/brain/index.js:68-82`) and `handleGetGoalDetail` (`:140-210`) both read every goal (explicit ∪ implicit union, parse, `resolveDecomposition`) — O(N) in goal count. - **The brain read module's import surface is SIX, quadruple-pinned** — `src/api/brain/index.js:23-28` (`lib/neo4j-driver`, `middleware/auth`, `utils/assistantKeys`, `lib/brain/goals`, `lib/brain/hygiene`, `lib/brain/resources`). - **The write template (ADR 0004).** `handleCreateResource` (`normalize/index.js:2485`) gates → validates → `serializeGoalWrite(() => createResource(...))`. The **mutex is at the handler**; the `createResource` **core** (`:2516`) is unserialized (resolve goal → `ensureResourceConcept` → dedup (goal, locator) → mint via `dtag.childDTag` + `publishToStrfry`/`importEventDirect`/`writeCypher SET ListItem` + `MERGE superset→elem`). Routes register at `registerNormalizeRoutes` (`:3980`).

## Options considered

### Option A — A new runtime-created **append-only** Work Record concept; two gated/serialized producers (`create-work-record` for `worked`, `note-goal-idea` for a `noted` session-attributed capture); append-only **by construction** (nonce d-tag, no dedup, never re-written); produced resources referenced by locator and resolved at read; a pure `work-records.js` core; the detail endpoint's `records` array populated (extensible to stories 6/7); a **new bounded `GET /api/brain/orient`**; the brain module gains its seventh require (planned four-suite re-pin)

Work Record is a new concept minted at runtime, self-bootstrapping on first use (mirroring External Resource, ADR 0004 d8). Every work record is a Work Record **element** carrying a `type` (`worked` | `noted`), the goal slug it is about (record-based linkage, d2), the session that produced it, a one-sentence summary, ≤2 questions, produced-resource locators, and a happened-on date. Both producers are gated normalize primitives serialized through the existing `serializeGoalWrite`, local-only. Append-only is **structural**: each write mints a fresh element under a nonce/random d-tag — there is no natural key and no dedup, so a write can never MERGE over a prior record, and nothing ever re-signs an existing one. The detail read groups Work Records by goal and projects each to the UI's record-entry shape, resolving produced locators against the goal's already-read resources into pointer cards. Orientation is a new, deliberately **bounded** read: a goal count, a capped slice of root goals, and (when asked) the served goal in full — a response whose size is flat as the corpus grows.

- **Pros:** honors every invariant by construction — append-only record (§7.2) is *structural*, not a checked constraint (a mint-only path cannot edit); the brain read module stays read-only (writes live in normalize; S6/S12 intact); record-based linkage survives export/restore + second-operator bootstrap (0001/0004); freshness/standing/produced all derived at read (§6; event-tagging 0009); refusals are system behavior (security 0001/0002); the one-spine stays a **read composition** (goal intent + resources + records, three concepts, one page) rather than a storage fusion; self-bootstrap makes a fresh instance work with zero manual steps (§5.9); orientation's bounded response is exactly the machine-persona token budget (§5.4); reuses the story-4 `createResource` core for produced resources (one agent call, no logic duplication, no nested mutex).
- **Cons:** a third net-new-concept bootstrap path (mitigated: idempotent, self-healing via the d8 fold, identical to ADR 0004's); two more normalize endpoints + one more brain read on already-large modules; the seventh brain require trips the quadruple pin (a planned positive re-pin — the recurring sibling-re-pin cost, now the fourth time, planned here in full); orientation reuses the O(N) corpus read server-side (its boundedness is a *response* property — see d11; a sub-linear server index is Phase 4, out of scope).

### Option B — Ledger-in-goal: store work records as an append array **inside the goal element**; orient by reading the goals list

Extend the goal's json with a `records: [...]` array; each write appends to it; the detail read returns the goal's own array; orientation reuses `GET /api/brain/goals`.

- **Cons (dispositive):** appending to the goal element **re-signs it on every work record** — `regenerateJson` resets `created_at` and rewrites durable intent, so the goal's capture date and intent history churn with volatile ledger writes; that is precisely the "append-only record vs durable intent" separation PRD §6/§7.2 forbids collapsing (the brain is *both* ledger and snapshot — not one row that is rewritten). It also loses attribution as an independent dated fact, cannot represent a record on a goal that no longer exists, and makes a session-born idea's `noted` fact a mutation of some *other* goal. Orientation via the goals list stays O(N) (fails AC1). Rejected — it violates the data model's foundational separation.

### Option C — Minimal-hatch: reuse `create-element`/`save-element-json` for records; reuse the goals list for orientation

Write records through the raw ungated-validation-free element hatches; validate in the conversational agent; orient off the existing list read.

- **Cons (dispositive):** the story's refusals (`too-many-questions`, `goal-not-found`, produced-must-be-attached, empty-field) become agent goodwill, not system behavior; builds on the **ungated, validation-free** `save-element-json`/`set-json-tag` hatches (flagged debt, ADR 0004 Consequences (c)); append-only is unenforced (the hatch can rewrite); AC5's session attribution + collision safety are unbuilt; orientation stays O(N) (fails AC1). Rejected — same disposition ADR 0003/0004 gave their Option C.

## Decision

We chose **Option A.**

Sub-decisions, each binding:

1. **Work Record concept (new, runtime-created, append-only).** Concept name **`tapestry work record`** → slug **`tapestry-work-record`** → header handle `39998:<TA>:tapestry-work-record` (TA runtime-resolved, never hardcoded). Single concept-object wrapper `jsonSchema.properties.workRecord` (satisfies the d8 fold's one-top-level-key requirement). Record fields (json `workRecord` section): `name` (a short machine label, e.g. `worked: <goal>` / `noted: <idea>`), `slug` (derived, unique per record — d3), `description` (machinery baseline — the summary), `type` (**enum `['worked','noted']`**), `goal` (the goal slug this record is about — d4), `session` (the producing session's label — d5), `summary` (the one-sentence standing), `questions` (list, **≤2** — d6), `produced` (list of locator strings — d4), `happenedOn` (ISO date). **`required`: `['name','slug','description','type','goal','session','happenedOn']`**; `x-tapestry.unique: ['slug']` (advisory; enforcement is structural — d3). All property descriptions plain-language (the fold mirrors `required` into the primary-property node).
2. **Two producers, one concept, distinguished by `type`.** Both `worked` and `noted` are Work Record elements. `worked` is emitted by `create-work-record` (d6); `noted` by `note-goal-idea` (d7). The design guide's other type words (`proposed`/`approved`/`skipped`) are **not** this story's — they arrive with the Proposal concept (story 6) and Priority Signal (story 7), which the read projection (d10) merges into the same `records` array later. Story 5 emits exactly `worked` and `noted`.
3. **Append-only by construction — the structural §7.2 guarantee.** Work records have **no natural key** and **no dedup**: each write mints a fresh element under a **nonce/random d-tag** (`dtag.childDTag(base, headerUuid, nonce)` with a per-write nonce, or `randomDTag()` — the Implementer's exact source), so two records that look identical are two distinct dated facts, and a write can **never** MERGE over a prior element. The `slug` is derived to be unique per record (the d-tag base incl. nonce). **Nothing ever re-signs or `regenerateJson`s a Work Record** — unlike External Resource (whose `verify` is a durable-intent update), a work record is written once and only read thereafter. There is no edit/verify/delete path. This makes "corrections are new facts" a property of the code, not a rule to be obeyed.
4. **Record-based linkage; produced resources referenced by locator, resolved at read.** `workRecord.goal` = the goal slug the record is about (the story-3/4 record-field idiom — no edge, no whitelist change). `workRecord.produced` = a list of **locator strings**. A produced resource is an **External Resource attached to the same goal** (ADR 0004): `create-work-record` **ensures** each produced `{locatorKind, locator, title}` is attached (calling the **unserialized `createResource` core** inside its own `serializeGoalWrite` task; a `resource-exists` result means "already attached — reference it"), and stores the locators. The detail read (d10) resolves `produced` locators against the goal's already-read resource set → pointer cards. A produced locator that resolves to no attached resource simply does not render (read-tolerant, mirroring ADR 0004's orphan tolerance). **One goal per record** (the served/noted goal); a record whose `goal` matches no goal renders nowhere (harmless orphan).
5. **Session identity = a caller-supplied label; no new auth surface.** The `session` field is a **caller-supplied string** on the write body (required, non-empty). It is recorded verbatim and dated by the record (`happenedOn` + the element `created_at`). There is **no new authentication mechanism** — the gate is the same `isOwner(req)||req.localTrusted` the other brain writes use; the session label is data the (already-gated) caller attests to. Because it is **owner-facing** (shown in the record entry, AC3), it must be a plain, readable label (a session name/date), not a jargon token — the copy discipline (d13) covers it. The captured goal's `origin` (d7) is likewise a plain provenance phrase.
6. **`POST /api/normalize/create-work-record`** (the `worked` producer; in `normalize/index.js` beside the goal-write primitives, registered in `registerNormalizeRoutes`). Gate first (`if (!isOwner(req) && !req.localTrusted) return 403`). Body `{goal:<slug>, session, summary, questions?:[…], produced?:[{locatorKind, locator, title, whyKept?, keywords?}]}`. Validation **before any write**: 400 for missing/empty `goal`/`session`/`summary`; refusal **`too-many-questions`** if `questions.length > 2` (the style-guide ≤2 rule as system behavior); resolve the goal (refusal `goal-not-found`/`ambiguous-slug`). Then, inside **one** `serializeGoalWrite` task: `ensureWorkRecordConcept()` (d8); for each `produced` spec, ensure it is attached to the goal via the `createResource` core (treating `resource-exists` as success — reference it; a genuine refusal like `unknown-kind` **fails the call**, named, nothing further written); mint the append-only `worked` element (d3) with `{workRecord:{type:'worked', goal, session, summary, questions, produced:[locators], happenedOn:today, name, slug, description:summary}}`, absent optionals omitted. Discriminated result `{success:true, result:'recorded', record:{slug, goal, type:'worked'}}`; refusals loud, named, HTTP-200 `{success:false, refusal, error}`, nothing written past the point of failure.
7. **`POST /api/normalize/note-goal-idea`** (the `noted` producer + session-attributed capture; same file/gate idiom). Body `{name:<idea name>, statement, session, servingGoal?}`. Validation before any write: 400 for missing/empty `name`/`statement`/`session`. Then, inside **one** `serializeGoalWrite` task: resolve the goal concept; run the **collision guard** (`createChildGoal`'s `name`/`slug`/d-tag check, `:2232`) → refusal `name-collides` (no parent needed — this is a **top-level** capture); mint the goal element `{tapestryOwnerGoal:{name, slug, description:statement, origin:<plain session-provenance phrase>, capturedOn:today}}` (no `parent` → a root goal; standing derives to `captured`); then `ensureWorkRecordConcept()` and mint an append-only `noted` Work Record on the **new goal** `{workRecord:{type:'noted', goal:<new slug>, session, summary:<the idea/why, incl. servingGoal context>, happenedOn:today, …}}`. **Nothing is launched** — the handler writes facts only; it has no code path that starts work or spawns a session (the v1 launcher is the owner; §7.3). Discriminated result `{success:true, result:'noted', goal:{slug, name}, record:{slug, type:'noted'}}`.
8. **Self-bootstrap `ensureWorkRecordConcept()`** (module-internal, idempotent) — a byte-for-byte structural copy of `ensureResourceConcept` (ADR 0004 d8): resolve the Work Record header; if present, return (so **no per-write churn** — `save-schema`, which re-signs the schema node, runs only when absent). If absent: `create-concept` (name `tapestry work record`, a plain description) treating "already exists" as success; `save-schema` with the complete d1 schema (the d8 fold reconciles the primary property in the same call); re-resolve. Runs inside the write path's `serializeGoalWrite` + owner/loopback gate, via `invokeNormalizeHandler`. **Never firmware-seeded** (§7.8); the first-run bootstrap is journaled at implementation with the complete schema JSON. Note: like External Resource, the concept self-provisions **per instance on first use** — staging/prod gain it on their first `create-work-record`/`note-goal-idea`.
9. **Serialization.** Both primitives run their read-validate-write bodies (including `ensureWorkRecordConcept` and any composed `createResource` core calls) through the **existing** `serializeGoalWrite` — **not renamed** (story-3 S5 / story-4 S4). The composed `createResource` **core** is unserialized (its mutex is at `handleCreateResource`), so there is **no nested-mutex deadlock**. One process-singleton queue serializes all brain mutations, so a work-record write never interleaves a read-validate-write race with a concurrent goal/resource write.
10. **Read surface — the `records` array populated; the brain module's seventh require.**
    - **`handleGetGoalDetail`** (`src/api/brain/index.js`) replaces the hardcoded `records: []` with a projection: read all Work Record elements (the **EXPLICIT ∪ IMPLICIT** union on `39998:<TA>:tapestry-work-record`, tolerant of the concept's absence — a fresh instance answers `[]`), group by goal, and for the winning goal project each record to the UI shape **`{date, type, summary, session, questions, produced}`** where `date` = `happenedOn`, `type` ∈ `worked`/`noted`, and `produced` is each locator **resolved against the goal's already-read resource set** into the pointer shape (`title, locatorKind, locator, freshness, freshnessDays`). Sorted **newest-`happenedOn` first** (`createdAt` tie-break) — consistent with the pointers' newest-first order and the morning-review "read downward" ergonomics. The array is **extensible**: stories 6/7 merge their concepts' projections here.
    - The brain module gains **exactly one require** — `require('../../lib/brain/work-records')` — the **seventh** spec. It stays **read-only** (no mutation/strfry tokens; S6/S12 green). This trips the quadruple-pinned import surface → a **planned positive re-pin of all four sibling allowlists in this same diff** (d15 / Test-class guidance).
11. **Bounded orientation `GET /api/brain/orient`** (new brain read; the AC1 surface). Gate `isOwner(req)||req.localTrusted → 403`. Optional `?goal=<slug>`. Returns `{success:true, goalCount, roots, served}` where:
    - `goalCount` = the total number of goals (a scalar);
    - `roots` = up to **`ORIENT_ROOT_CAP`** (a named constant, 24) **root** goals (parent-less in the resolved forest), each `{slug, name, standing}` — a **bounded slice** of "what exists"; when `goalCount` exceeds it, the session knows there is more;
    - `served` = when `?goal` resolves, the served goal **in full** — `{slug, name, statement, standing, captureDate, deliverable, boundary, parentSlug, parentName, ancestry:[…]}`, **deliverable/boundary verbatim** — else `null`.
    **Boundedness is a property of the response** (the machine persona's token budget, §5.4): the payload size is flat as N grows past the cap (`roots` capped; `served` is one goal + bounded ancestry; `goalCount` a scalar). The endpoint reuses the existing O(N) `readResolvedGoals` **server-side** (identical to the list/detail reads) — a *sub-linear server index* is **Phase 4** (PRD §8.3), explicitly out of scope; the AC1 contract the Tester demonstrates is response-boundedness. Orientation is **agent-facing** (the conversational session reads it) — **no UI hook or page** is added.
12. **UI — extend the record entry; disposition the findings.** `ui/src/pages/brain/GoalDetail.jsx`:
    - **`RecordEntry`** grows to render, below the existing `date`/`type`/`summary` line: the **session** attribution, the **≤2 questions** (plain lines), and the **produced pointers** as `PointerCard`s (reusing the story-4 component). **No edit/delete affordance** at the entry level, ever (AC6; story-4 S7 contract, now with live entries — the Tester re-pins it).
    - **OPEN.md row 87(a)** — `freshnessLine` (`:36-41`): drop the **dead** `current`-branch null fallback (`'verified recently'` — the server never returns `current` with a null day-count), simplifying to `verified ${n} days ago`; **retain** the `stale`-branch `'not verified recently'` fallback (the design guide's degraded surface; reachable only via the flagged raw hatch). *Disposition: fixed (dead branch) + ratified (stale fallback).*
    - **OPEN.md row 87(b)** — the `Resources` / `Record` `<h2>` section headings (`:170,182`): **ratified and pinned**. They are plain-language (`Record` is the design guide's own term), jargon-clean, and now carry more weight (produced pointers nest inside records) — they aid the one-spine's readability. *Disposition: ratified; the Tester pins them so the Reviewer does not re-flag.*
    - **OPEN.md row 87(c)** — the raw-`locator` `href` for all kinds (`:49-55`): **ratified** for v1. AC3's testable contract (no embed/fetch; `target=_blank rel=noopener`) holds; a kind-specific scheme map (nostr-event→njump/`nostr:`, file→a file scheme) is a deferred refinement, not this story's. *Disposition: ratified; deferral recorded.*
    - **OPEN.md row 86(b)** — the href-less `<a onClick>` Retry (not keyboard-focusable): **fixed** by swapping to an accessible `<button className="brain-retry" onClick={refetch}>Retry</button>` in **both** surfaces the row names — `GoalDetail.jsx:126` **and** `ui/src/pages/brain/Goals.jsx` (story-1's twin). `styles.css` gives `.brain-retry` a button reset (link appearance, no new tokens). *Disposition: fixed, both surfaces.*
13. **Copy discipline.** All new owner-facing strings — the `worked`/`noted` type words, the session-attribution chrome, the question lines, the captured goal's `origin` phrase — come verbatim from / conform to the style guide and pass the banned-jargon scan (*element, kind, schema, event, pubkey, superset, concept header, persona, acceptance criteria, lease, payload, endpoint*), no exclamation marks. `session` values are owner-facing plain labels. The story-3/4 `GoalDetail` jargon scan (S9/S8) **extends** over the new strings. (`event` remains whitelisted only as the design-guide pointer-kind marker — unchanged from ADR 0004 d11.)
14. **Conversational contract addendum** (ADR 0001 d1 / 0003 d12 / 0004 d12 grow; doc-only, no code obligation this story): a session **orients** via `GET /api/brain/orient` (optionally `?goal=<slug>`); **records work** via `POST /api/normalize/create-work-record`; **notes a session-born idea** via `POST /api/normalize/note-goal-idea`. The agent utters the one-sentence confirmations itself (API responses are never owner-facing).
15. **Constants.** `ORIENT_ROOT_CAP = 24` (bounded orientation slice) and `MAX_QUESTIONS = 2` (the ≤2 rule) are single named constants (`ORIENT_ROOT_CAP` in `src/api/brain/index.js`; `MAX_QUESTIONS` in `normalize/index.js`), tunable in one place.

## Consequences

- **Enables:** the session read/write loop end-to-end — a session orients at flat cost and leaves an append-only, attributed, dated record on the goal it served; the one-spine Goal detail finally shows live records (intent + pointers + record, three concepts on one page); a session-born idea is captured and visible without launching anything; the `records` array is the extension seam stories 6/7 plug into; the Work Record is the raw material of the Phase-3 morning review (built later, not now). The bounded orient is the first corpus-independent read — the machine persona's load-bearing tolerance, satisfied.
- **Constrains:** the goal↔record and record↔resource linkages are **record-based** — any future edge materialization must supersede this ADR **and** go through the relationship-primitives whitelist path; work records are **append-only with no edit/verify/delete** (a retract/correct flow, if ever wanted, is a new append, not a mutation); one goal per record in v1; the brain module stays read-only (record **writes** live in normalize). Orientation's server-side read stays O(N) until a Phase-4 index.
- **Debt / follow-ups:** (a) Work Record is **not yet covered by the hygiene check** (`HYGIENE_CONCEPTS` stays the two work-item concepts) — a dangling-`goal`-reference / dangling-`produced`-locator classifier for records is a natural later addition; the read path is already tolerant. (b) The raw `save-element-json`/`set-json-tag` hatches can still write unvalidated record fields — pre-existing flagged debt, compensated by read-time tolerance. (c) Orientation returns a **capped** `roots` slice with no paging — a `?after=`/cursor is a later addition if a corpus outgrows the cap in a way the count alone doesn't serve. (d) `note-goal-idea`'s captured goal is a **root** (no parent) in v1 — attaching a session-born idea under a parent is a later decision. (e) ~30 lines of concept-lookup Cypher mirrored from `createResource`/`createChildGoal` — accepted, as ADR 0003/0004 accepted it.
