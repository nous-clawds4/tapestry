**Status:** Accepted
**Date:** 2026-07-24
**Story:** `engineering-team/stories/second-brain/7-teach-it-what-matters.md`
**Builds on:** second-brain ADR 0006 — this story is the **third producer** of the goal-detail `records` array (the ADR 0005 d10 extension seam, built for "stories 6/7"). It reuses ADR 0006's runtime-created-concept pattern (`ensureProposalConcept` → `ensureSignalConcept`), the append-only-by-construction mint (`mintProposalElement` → `mintSignalElement`; nonce/random d-tag, never `regenerateJson`), the pure-core + read-time-derivation idiom (`proposals.js` → `signals.js`), the record-based-linkage idiom (goal slugs in the record, no edges), and the gated/validated/serialized/local-only write pattern. ## Options considered

### Option A — one append-only element per signal; the two-goal spine fan-out at READ; a single gated producer with server-stamped framing; no new UI and no new brain route

A new runtime-created `tapestry-priority-signal` concept holds one element per recorded choice — **single shape, no `type` enum, no lifecycle** (a signal is born final; there is nothing to decide about it later). The element records `prefers` + `over` (goal slugs — record-based linkage), optional `reason`, `judgedBy`, `judgedOn`, `framing`. One producer `POST /api/normalize/record-priority-signal` validates (both goals resolve, distinct; **no viability requirement**) and mints append-only. At read, `groupSignalsByGoal` projects **each signal under BOTH slugs**; `handleGetGoalDetail` merges side-worded entries into the existing `records` spine. The framing is a **server-stamped named constant** in v1 — no caller parameter. No new view, no new brain GET route: the goal detail carries the entries, and the conversational lane cites signals by reading goal details (AC4's soft affordance).

- **Pros:** one stored fact per judgment — the pair **is** the entity (PRD §6: "Priority Signal — prefers goal / over goal…"); both spine views are **derived at read** (invariant 3 / filter-at-view-time; event-tagging 0009), so the two sides can never diverge and a future goal-rename changes both renderings for free; append-only is structural (mint-only path, no `regenerateJson` anywhere in it); the framing-as-stamped-constant keeps §7.6 honest (a caller-suppliable framing **is** the swap hatch the constitution defers to owner ratification — not building it is the point); no-new-UI honors the three-view inventory and "data for the future, not a feature surface"; the concept bootstrap, mint, core, and projection are byte-familiar idioms (fourth repetition), minimizing novel surface; zero UI diff means the jargon/no-numeric scans concentrate on one file's wording templates.
- **Cons:** the goal-detail read now scans a **third** concept (signals) on every detail request — O(N) like its siblings (the Phase-4 index remains deferred); the ninth require trips the sextuple pin (planned re-pin across six suites — the recurring cost, planned here); side-specific wording needs the *other* goal's display name at projection time (handler-side name lookup — the established handler-side-resolution pattern); a two-word type word ("passed over"), if ratified, extends the design guide's record vocabulary (book-close back-fill).

### Option B — fan-out at WRITE: mint two elements per choice, one per touched goal

Each recorded choice mints **two** elements (a "preferred" fact on the prefers-goal, a "passed over" fact on the over-goal), each carrying the single `goal` slug its side is about — reusing the exact one-goal grouping the other concepts use.

- **Cons (dispositive):** it stores **one judgment as two facts that can diverge** — a half-written pair (crash between mints) leaves a signal visible on one spine and absent from the other, violating AC3's both-spines guarantee at the storage layer rather than deriving it; export (story 8) would carry two artifacts for one owner act, and any future aggregation must first re-join the pair; it doubles write volume for zero read simplification (the read must *still* recognize pairs to render "chose this over X" with the other goal named). The §6 entity is *one* signal with two goal references — splitting it is denormalization of exactly the kind invariant 3 warns against. **Rejected.**

### Option C — reuse the `tapestry-proposal` concept (new types `preferred`/`passed-over`), or the raw ungated hatches

Either (C1) extend `PROPOSAL_TYPES` and mint signals as proposal elements — the concept machinery already exists; or (C2) write signals through `save-element-json`/`set-json-tag` and validate in the agent.

- **Cons (dispositive):** C1 conflates two §6 entities the PRD defines separately (Proposal: nominates/why-now/passed-over-list/decision; Priority Signal: prefers/over/judged-by/framing) — the shared schema would carry both entities' fields as optional mush, `openProposals` would need to learn to ignore signal types, story 8's export names them as distinct content, and the hygiene future gets muddier. The Work Record precedent (one concept, multiple types) covers *one entity's* fact variants, not two entities. C2 is the ungated-hatch anti-option every prior ADR rejected: the exists/distinct refusals and the framing stamp become agent goodwill, not system behavior. **Rejected** — same disposition as ADRs 0003–0006 gave their Option C.

## Decision

We chose **Option A.** Sub-decisions, each binding:

1. **Concept (new, runtime-created, append-only, single-shape).** Concept name **`tapestry priority signal`** → slug **`tapestry-priority-signal`** → header handle `39998:<TA>:tapestry-priority-signal` (TA runtime-resolved, never hardcoded). Single concept-object wrapper `jsonSchema.properties.prioritySignal` (satisfies the d8 fold's one-top-level-key requirement). Fields (json `prioritySignal` section, all descriptions plain-language): `name` (machine label, `preferred: <prefers> over <over>`), `slug` (derived, unique per element), `description` (a neutral static sentence — the machinery baseline), `prefers` (the chosen goal's slug), `over` (the passed-over goal's slug), `reason` (the optional one-line reason), `judgedBy` (who judged), `judgedOn` (ISO date), `framing` (the framing tag that produced this signal). **`required`: `['name','slug','description','prefers','over','judgedBy','judgedOn','framing']`** (AC2's all-three-present is schema-level; `reason` is the one optional field); `x-tapestry.unique: ['slug']` (advisory; enforcement structural). **No `type` enum** — unlike Work Record/Proposal, a signal has exactly one fact shape; the *spine* type words (d5) are a **projection concern**, derived per side at read, not stored.
2. **No lifecycle, no dedup, no natural key.** A signal is **born final** — there is no open/decided state, no verification, no supersession. The same pair may be chosen again any number of times (each a new dated fact — the corpus accumulating, including reversals); recording B-over-A never touches an earlier A-over-B. Append-only by construction: every write mints a fresh element under a **nonce/random d-tag** via `mintSignalElement` (byte-mirroring `mintProposalElement`); **nothing on the signal path ever `regenerateJson`s or re-signs.**
3. **Record-based linkage; the pair is one fact.** `prefers` and `over` are goal **slugs** (the story-3→6 record-field idiom — no edge, no whitelist change). A signal whose slugs match no live goal renders nowhere for that side (harmless orphan; read-tolerant, mirroring siblings). The **two-goal spine fan-out happens at READ** (the load-bearing call): `groupSignalsByGoal` returns each signal under **both** its `prefers` key and its `over` key, and the goal-detail projection words each side from that goal's perspective. One stored fact, two derived views — the sides cannot diverge.
4. **No standing requirement on either goal (ratified at the Architecture gate — story Open Q2).** The producer validates that both goals **resolve** (exist, unambiguous) and are **distinct** — nothing else. A parent, `captured`, or otherwise non-viable goal may be preferred or passed over (the owner is teaching relative value, not certifying execution-readiness). Refusals: `goal-not-found` (either slot; the error names the offending slug), `ambiguous-slug`, `same-goal` (the two inputs name the same goal).
5. **Owner-facing wording — RATIFIED at the Architecture gate (operator, 2026-07-24; the story's Open Q1/Q4, the ADR 0006 d16 precedent).** The strings below are canonical verbatim; the Reviewer treats any deviation as a blocking copy defect; back-filled into the guides at book-close:
   - **Spine type words (side-specific pair, recommended):** **`preferred`** on the preferred goal's spine; **`passed over`** on the other. Rationale: at-a-glance direction on each side; "passed over" is already the product's own vocabulary (PRD §6, the queue, the proposal card's runner-up language); both are calm past-tense words like the existing five, and the recon confirms a two-word type renders as plain text. *(Named alternative: one neutral word — `compared` — on both sides; rejected-by-default because the direction then lives only in the summary.)*
   - **Spine summaries** (derived at read; `{other}` is the other goal's current display name, straight-quoted; when a reason exists it folds on after an em-dash — one line, both sides):
     - preferred side: `chose this over "{other}"` / with reason: `chose this over "{other}" — {reason}`
     - passed-over side: `"{other}" chosen over this` / with reason: `"{other}" chosen over this — {reason}`
   - **Capture confirmation** (uttered by the conversational lane; the UI renders nothing new): **`Noted — "{prefers}" over "{over}".`** (register family of *"Skipped — noted."*; names, not slugs).
   - The elicitation prompt stays the PRD's verbatim **"solve one today: which?"** (conversational contract, d11). All strings pass the banned-jargon scan and contain **no numerals**.
6. **`POST /api/normalize/record-priority-signal`** (the single producer; conversational-lane/owner-invoked, **no UI trigger**; in `normalize/index.js` beside the story-5/6 producers, registered in `registerNormalizeRoutes`). Gate first (`if (!isOwner(req) && !req.localTrusted) return 403`). Body **`{prefers, over, reason?}`**. Shape validation before anything: 400 for missing/non-string/empty `prefers` or `over`; 400 for a supplied non-string `reason`; a supplied-but-blank `reason` is treated as absent (optional means optional). Then, inside **one** `serializeGoalWrite` task (`recordPrioritySignal` core): trim inputs; **`same-goal`** refusal when `prefers === over`; resolve goals (`resolveGoalConcept` + `fetchGoalRecords` + `resolveDecomposition`, the `makeProposal` idiom) with `goal-not-found`/`ambiguous-slug` refusals per slot; **no viability check** (d4); then `ensureSignalConcept()` (d7); mint the append-only element `{prefers, over, reason?, judgedBy, judgedOn: today, framing: SIGNAL_FRAMING_V1}` with `description` = `chose "{prefersName}" over "{overName}"` (names as resolved at write — a static baseline; the *rendered* spine strings derive from current names at read). Result `{success: true, result: 'recorded', signal: {uuid, slug, prefers, over}}`. Refusals loud, named, HTTP-200 `{success:false, refusal, error}`, nothing written past the point of failure.
7. **`judgedBy: 'owner'` (v1 constant).** V1 has exactly one judge; the literal `'owner'` is **instance-relative** — it stays true for a second operator's export/restore and never bakes a reference-instance identity into owner data (§5.9). A future multi-judge world extends the vocabulary with new values; nothing re-labels history. *(Named alternative — record the owner's pubkey: rejected for v1; it couples exported judgment history to a key identity for zero v1 benefit.)*
8. **`framing: SIGNAL_FRAMING_V1 = 'solve-one-today'` — a server-stamped named constant; NO caller parameter.** The v1 elicitation is the PRD's canonical pairwise question; the recording lane stamps its tag on every signal (AC2). A caller-suppliable framing is deliberately **not** built: §7.6 makes framing replacement an owner-ratified act with evidence — the parameter *is* the swap hatch, and it arrives with that Phase-2+ mechanism, not before. AC5's interpretability guarantee is carried by **storage**: the tag lives on each element and every read returns the stored value (the pure core preserves per-row tags; U-tests prove distinct tags coexist; no read path consults a global).
9. **Self-bootstrap `ensureSignalConcept()`** — a structural copy of `ensureProposalConcept` (`normalize/index.js:3069`): resolve; if present return (no per-write churn); else `create-concept` (name `tapestry priority signal`, plain description: *"A dated, append-only record of the owner choosing one goal over another — who judged, when, and under which framing. Never edited; a changed mind is a new signal."*) treating "already exists" as success + `save-schema` with the d1 schema (the d8 fold reconciles the primary property) + re-resolve. Runs inside the producer's `serializeGoalWrite` + gate, via `invokeNormalizeHandler`. **Never firmware-seeded** (§7.8); self-provisions per-instance on the first live signal; first-run bootstrap journaled at implementation with the schema JSON.
10. **Read surface — the spine gains the signal projection; the brain module's ninth require; NO new route.**
    - **New pure core `src/lib/brain/signals.js`** (zero-require CJS, the `proposals.js` precedent): `parseSignalRow(row)` (whitelisting parser → `{uuid, name, slug, description, prefers, over, reason, judgedBy, judgedOn, framing, createdAt}`; malformed/non-signal rows → `null`, never throws), `groupSignalsByGoal(records)` → `Map<goalSlug, record[]>` where **each valid record appears under BOTH `prefers` and `over`** (records missing either slug, or with `prefers === over`, are dropped as malformed), and `signalEntry(record, side, otherGoalName)` → `{date: record.judgedOn, type, summary}` carrying the **d5 wording templates** (side ∈ `'prefers' | 'over'`; `otherGoalName` falls back to the other slug when the goal is gone — read-tolerant). The templates live **here**, in the pure core: U-testable verbatim, jargon-scannable in one place.
    - **`src/api/brain/index.js`** — `SIGNAL_CONCEPT_SLUG = 'tapestry-priority-signal'`; `readSignals(taPubkey)` (the EXPLICIT ∪ IMPLICIT union on the signal header, absence-tolerant — byte-mirrors `readProposals` at `:135-146`); in `handleGetGoalDetail`, a third entry array: group signals, take the winner-slug bucket, for each compute `side` (`r.prefers === winner.slug ? 'prefers' : 'over'`), resolve the other goal's name from the already-loaded `resolved` set (`resolved.find(g => g.slug === otherSlug)` — the parent-lookup idiom at `:277`), project via `signalEntry` + `{session:null, questions:[], produced:[], _createdAt}`, spread into the existing merge-and-sort (`:268-275` — unchanged machinery). The module gains **exactly one require** — `require('../../lib/brain/signals')` — the **ninth** spec; it stays **read-only** (no mutation/strfry tokens). **No new GET route**: `registerBrainRoutes` (`:543-549`) is untouched — the goal detail is the visibility surface (AC3), and the conversational lane cites signals from goal-detail reads (AC4's soft affordance needs no dedicated endpoint).
11. **Conversational contract addendum** (ADR 0001 d1 / 0003 d12 / 0004 d12 / 0005 d14 / 0006 d14 grow; doc-only, no code obligation this story): the agent elicits with the canonical question verbatim — *"solve one today: which?"* — records the owner's answer via `POST /api/normalize/record-priority-signal` (passing `reason` only when the owner gave one), and utters the d5 confirmation. It may cite recorded signals in a later proposal's why-now **in plain words** (reading them off goal details); it never wires them into `make-proposal` mechanically.
12. **Copy discipline.** All new owner-facing strings are the d5 set — the two type words, the two summary templates (+ reason fold), the confirmation. They pass the banned-jargon scan (*element, kind, schema, event, pubkey, superset, concept header, persona, acceptance criteria, lease, payload, endpoint*), contain **no exclamation marks and no numerals** (AC6 — counts included; nothing owner-facing ever tallies signals). The `reason` is owner-authored plain content. The story-3→6 jargon scan extends over `signals.js` (the templates' home). `Proposals.jsx` and all existing UI are untouched.
13. **Constants.** `SIGNAL_FRAMING_V1 = 'solve-one-today'` and `SIGNAL_CONCEPT_NAME = 'tapestry priority signal'` in `normalize/index.js`; `SIGNAL_CONCEPT_SLUG` in `brain/index.js`. No arity/length bounds needed (the pair is fixed arity; the reason mirrors the skip reason — a free one-liner, unbounded like its sibling).
14. **Untouchables (byte-unchanged):** `ui/src/pages/brain/GoalDetail.jsx` (**newly byte-pinned this story** — the projection fits `RecordEntry` as-is), all other `ui/src/**` (zero UI diff), `src/api/normalize/relationships.js`, `probe.js`, `src/middleware/auth.js` (incl. `PUBLIC_MUTATIONS`), `firmware/`, the four ADR-0015 `LEGACY_*` files, `nostrPublish.js`. `serializeGoalWrite` not renamed; `makeProposal`/`decideProposal` unchanged (no signal consumption — AC4); no relationship-whitelist edge; `HYGIENE_CONCEPTS` unchanged; no new `:root` tokens (trivially — no styles touched).

## Consequences

- **Enables:** the owner's relative-value judgment accumulates as dated, attributed, framing-tagged, append-only facts, visible on both touched goals' spines and citable by future proposals in words — the raw corpus for the Phase-2/3 selection engine and framing iteration, with §7.6's interpretability guarantee structural (per-element framing tags). The PRD §6 entity set now has live producers for five of six entities (Category instances remain the epic's recorded gap). Story 8's export has signals to carry.
- **Constrains:** signal↔goal linkage is record-based (any future edge materialization supersedes this ADR through the whitelist path); signals are append-only with no retract/edit (a reversal is a new signal); the framing is fixed to the v1 constant until a ratified swap mechanism arrives (Phase 2+, new ADR); goal-detail reads now scan three record concepts (O(N) each, the codebase's standard derive-at-read cost; the sub-linear index stays Phase 4); the spine vocabulary grows by the ratified d5 words (guide back-fill at book-close).
- **Debt / follow-ups:** (a) Priority Signal is **not hygiene-covered** (`HYGIENE_CONCEPTS` unchanged — dangling `prefers`/`over` slugs are read-tolerated; a classifier is a natural later addition beside the proposal one). (b) The raw `save-element-json`/`set-json-tag` hatches can still write unvalidated signal fields — pre-existing flagged debt, compensated by read-time tolerance. (c) `judgedBy:'owner'` is a v1 single-judge constant — multi-judge attribution is a future vocabulary extension, not a migration. (d) The d5 strings + type words + the elicitation prompt need **style/design-guide back-fill at book-close** (with the ADR 0006 d16 approve string — one return-edge bundle).
- **Firmware reinstall required? No.**
