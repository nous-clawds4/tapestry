# ADR 0006: The proposal loop — a new append-only `tapestry-proposal` concept (runtime-created, never mutated), type-discriminated (`proposed`/`approved`/`skipped`), decisions appended as separate facts referencing the proposal, open-ness derived at read; three gated/serialized producers (`make-proposal` + `approve-proposal` + `skip-proposal`); the goal-detail `records` array gains the proposal projection (8th brain require); a bounded queue read `GET /api/brain/proposals`; and a new owner-gated Proposal-queue view

**Status:** Accepted
**Date:** 2026-07-24
**Story:** `engineering-team/stories/second-brain/6-the-proposal-loop.md`
**Builds on:** second-brain ADR 0005 — this story is the **second producer** of the goal-detail `records` array ADR 0005 d10 built as an explicit extension seam ("Extensible — stories 6/7 merge their concepts' projections into this same array"). It reuses ADR 0005's runtime-created-concept pattern (`ensureWorkRecordConcept` → `ensureProposalConcept`), the append-only-by-construction mint (`mintWorkRecordElement` → `mintProposalElement`; nonce/random d-tag, never `regenerateJson`), the pure-core + read-time-derivation idiom (`work-records.js` → `proposals.js`), the record-based-linkage idiom (d4), and the gated/validated/serialized/local-only write pattern. ADRs 0001 (capture contract; adopt element machinery; derived-not-stored standing; read seam), 0002 (read-only brain module), 0003 (`serializeGoalWrite`; validated goal writes; the collision guard; the d8 save-schema fold), 0004 (runtime-created concept + self-bootstrap; the `verifyResource` **durable-intent** update) all remain binding.

## Context

The story (`6-the-proposal-loop`, gate-approved 2026-07-24). Acceptance criteria, quoted to confirm:

- **AC1** — a proposal nominates **exactly one viable goal** (a leaf with deliverable+boundary; never a parent/non-viable goal), with a why-now in 1–2 plain sentences and **named runners-up each with a one-line why-not**, in the canonical register.
- **AC2** — the **Proposal queue** (the third owner-gated view) renders open proposals as the design guide's **emphasis cards** with **equal-weight Approve / Skip…**; verbatim empty + error states.
- **AC3** — Approve records a dated **`approved`** decision, retires the proposal from the queue, and shows on the nominated goal's spine; **launches nothing** (the owner launches in v1).
- **AC4** — Skip **requires a one-line reason** (disabled until non-empty), records **`skipped`** + reason, confirms *"Skipped — noted."*
- **AC5** — standing is exactly **`open` / `approved` / `skipped`**; transitions **only** by an owner act (no auto-decide, **no auto-expiry**); the full lifecycle is legible on the nominated goal's **one spine**; record entries are **append-only** (no edit/delete affordance; a decision never rewrites a seen entry).
- **AC6** — **no numeric score** in any owner-facing proposal copy.
- **AC7** — jargon-clean verbatim copy; Proposal is **new/append-only/runtime-created/never-firmware-seeded/TA-runtime-resolved**; stories 1–5 suites still pass (the `records` projection now also carries `proposed`/`approved`/`skipped`).

## Options considered

### Option A — a new runtime-created **append-only** Proposal concept, **type-discriminated** (`proposed`/`approved`/`skipped`); decisions appended as **separate facts** referencing the proposal by a stable `proposalId`; **open-ness derived at read**; three gated/serialized producers (`make-proposal` validates a caller-supplied nomination against the live graph and records it; `approve-proposal`/`skip-proposal` append a decision); a pure `proposals.js` core; the goal-detail `records` array gains the proposal projection (8th brain require, planned five-suite re-pin); a bounded `GET /api/brain/proposals` queue read; a new owner-gated Proposal-queue view + route + nav

Proposal is a new concept minted at runtime, self-bootstrapping on first use (mirroring External Resource / Work Record). It holds append-only **elements with a `type` discriminator** — exactly the Work Record shape (`worked`/`noted`) — where `proposed` is the nomination and `approved`/`skipped` are decisions. A decision **does not mutate** the proposed element; it appends a separate `approved`/`skipped` element carrying the proposal's stable id. "Is this proposal still open?" is **derived at read** from whether any decision references its `proposalId` — never stored as a flag that overwrites the nomination. Both the nomination and its decision carry the same nominee `goal` slug, so both project onto that goal's spine (the goal gets its `proposed`/`approved`/`skipped` entries **for free**). `make-proposal` is the honest **validator + recorder**: the gated caller supplies the nomination and rationale (the *selection heuristic* is the caller's — deliberately unspecified, PRD §5.5/story note), and the server **re-reads the live graph and refuses** unless the nominee is currently a viable leaf and the runners-up are real, distinct viable goals. The decisions are triggered by the owner-gated Proposal-queue UI (Approve/Skip buttons).

- **Pros:** honors every invariant by construction — append-only record (§7.2) is *structural*, not a checked constraint (a mint-only path cannot edit; the whole proposal path is free of `regenerateJson`); the decision-as-separate-fact keeps the nomination immutable **and** hands the goal's spine its `approved`/`skipped` entries for free; open-ness is **derived at read** (invariant 3 / filter-at-view-time; event-tagging 0009), never a stored subjective flag; the brain read module stays read-only (writes live in normalize; the story-5 S13-equivalent pin intact); record-based linkage survives export/restore + second-operator bootstrap; self-bootstrap makes a fresh instance work with zero manual steps (§5.9); the type-discriminator reuses the Work Record shape exactly (one more mint idiom, one more pure core, one more projection — no new machinery); the selection judgment lives **in the brain** as the recorded Proposal element, not a scheduler-side log (§7.1); `make-proposal` grounds the recorded proposal in **live graph state** (viable-leaf verified server-side), so AC1's "a non-viable nominee is refused" is system behavior, not caller goodwill.
- **Cons:** a third net-new-concept bootstrap path (mitigated: idempotent, self-healing via the d8 fold, byte-identical to ADR 0004/0005); three new normalize endpoints + one new brain read on already-large modules; the eighth brain require trips the quintuple pin (a planned positive re-pin — the recurring sibling-re-pin cost, now the fifth time, planned here in full); "is it open?" costs a **read-time join** (partition by `type`, match decisions to proposeds by `proposalId`) — O(P) in proposals, the codebase's standard derive-at-read cost; the first **owner-facing UI write** in the brain surface (a deliberate, scoped departure from the epic's "no new UI form" — the design guide mandates the interactive card).

### Option B — in-place decision: keep **one** Proposal element per proposal and mutate its `decision` field (`open → approved | skipped`) via `regenerateJson`, the `verifyResource` way

One `proposed` element carries `decision:'open'`; approve/skip fetch it, set `decision`/`reason`/`decidedOn`, and `regenerateJson`. The queue reads elements with `decision==='open'`; the spine derives entries from the element's `madeOn` + `decidedOn`.

- **Cons (dispositive):** it **mutates an append-only entity.** §6 classifies External Resource as *durable intent* (which is why `verifyResource`'s in-place `regenerateJson` is licensed there) but classifies **Proposal as *append-only***; §7.2 explicitly lists **proposals and decisions** among facts "never edited or deleted." Mutating the proposal to stamp its decision contradicts the entity's own §6 classification and the §7.2 letter. It also re-signs the proposal element on every decision (churning `created_at`), collapses the ledger toward "latest state" (the lifecycle must be *reconstructed* by deriving two entries from one element's date fields, rather than being two standalone facts), and makes a stored `decision` flag the source of open-ness — the exact "store the subjective result" anti-pattern invariant 3 / event-tagging 0009 warn against. Simpler read, but it trades the story's structural §7.2 guarantee for convenience. **Rejected** — this is the load-bearing question the story deferred to Architecture (Open Q #1), and the §6 durable-intent-vs-append-only distinction is decisive against it.

### Option C — a separate third **Decision** concept (proposals immutable; decisions in their own concept), or the minimal ungated hatch

Either (C1) mint proposals in `tapestry-proposal` and decisions in a *second* new `tapestry-decision` concept, joined at read; or (C2) write proposals/decisions through the raw `save-element-json`/`set-json-tag` hatches and validate in the agent.

- **Cons (dispositive):** C1 doubles the bootstrap + read surface (two concepts, two self-bootstraps, two projections) for **no gain over Option A's type discriminator** — the Work Record precedent already shows one concept cleanly holds multiple append-only fact types by `type`. C2 builds on the **ungated, validation-free** hatches (flagged debt, ADR 0004/0005 Option C): the viability gate, the decided-exactly-once guard, and `reason-required` become agent goodwill rather than system behavior, and append-only is unenforced. **Rejected** — same disposition ADR 0003/0004/0005 gave their Option C, plus C1's redundancy.

## Decision

We chose **Option A.** Sub-decisions, each binding:

1. **Proposal concept (new, runtime-created, append-only).** Concept name **`tapestry proposal`** → slug **`tapestry-proposal`** → header handle `39998:<TA>:tapestry-proposal` (TA runtime-resolved, never hardcoded). Single concept-object wrapper `jsonSchema.properties.proposal` (satisfies the d8 fold's one-top-level-key requirement). Fields (json `proposal` section): `name` (a short machine label, e.g. `proposed: <goal>` / `approved: <goal>` / `skipped: <goal>`), `slug` (derived, unique per element — d3), `description` (machinery baseline — the spine summary), `summary` (the one-line spine summary — d10), `type` (**enum `['proposed','approved','skipped']`**), `goal` (the nominated goal's slug this fact is about — d4), `whyNow` (the why-now; on `proposed`), `passedOver` (list of `{goal, whyNot}`; on `proposed`), `proposalId` (the referenced `proposed` element's slug; on decisions — d4), `reason` (the required skip reason; on `skipped`), `happenedOn` (ISO date — made-on for `proposed`, decided-on for decisions). **`required`: `['name','slug','description','type','goal','happenedOn']`** (mirrors Work Record — type-specific fields vary by `type`, so they are not globally required; the write path is the enforcer); `x-tapestry.unique:['slug']` (advisory; enforcement is structural — d3). All property descriptions plain-language.
2. **One concept, three record types, distinguished by `type` (the Work Record precedent).** `proposed` (the nomination, from `make-proposal`, d6) and `approved`/`skipped` (decisions, from `approve-proposal`/`skip-proposal`, d7) are all Proposal elements. `PROPOSAL_TYPES = ['proposed','approved','skipped']`. These are exactly the design guide's other three record type words; the goal-detail read (d10) merges them into the **same** `records` array beside story 5's `worked`/`noted`. The design guide's five type words are now fully realized (stories 5 + 6).
3. **Append-only by construction — the structural §7.2 guarantee (the load-bearing decision, resolved to shape (b)).** Proposal elements have **no natural key** and **no dedup**: every write (all three producers) mints a fresh element under a **nonce/random d-tag** via a shared `mintProposalElement` (byte-mirroring `mintWorkRecordElement`), so a write can **never** MERGE over a prior element. **A decision never mutates the proposed element** — approve/skip **append** a separate `approved`/`skipped` fact referencing the proposal by `proposalId`. **Nothing on the proposal path ever `regenerateJson`s or re-signs.** "Corrections are new facts" (§7.2) is a property of the code, not a rule to obey. *Why shape (b) not (a): §6 classifies Proposal as append-only (unlike durable-intent External Resource, the sole licence for `verifyResource`'s in-place update); §7.2 names proposals and decisions among facts never edited; and (b) yields the goal's spine `approved`/`skipped` entries for free — see Option A vs B.*
4. **Record-based linkage; the decision references the proposal by a stable `proposalId`.** `proposal.goal` = the nominee slug (the story-3/4/5 record-field idiom — no edge, no whitelist change); both the `proposed` element and its decision carry the **same** `goal`, so both project onto the nominee's spine. The **passed-over** goals get **no** spine entry (they were not chosen; recording "passed over" on each runner-up's spine would be noise — AC5 scopes visibility to the *nominated* goal). `proposal.proposalId` on a decision = the `proposed` element's `slug` (unique per proposal). A decision whose `proposalId` matches no `proposed` element renders nowhere (harmless orphan; read-tolerant, mirroring ADR 0004/0005).
5. **The nominee is verified viable-leaf at write, against the live graph (the honest anchor); the selection heuristic is the caller's.** `make-proposal` is the honest **validator + recorder**. The gated caller (owner / loopback conversational agent) supplies `{goal, whyNow, passedOver:[{goal, whyNot}]}`; the server **re-reads the goals, resolves decomposition + standing, and refuses** unless the nominee is currently a **viable leaf** (`deriveStanding(resolved, {hasChildren}) === 'viable'`) — a parent or non-viable/`captured`/`achieved`/`abandoned` goal is refused (`not-viable`), satisfying AC1's "a non-viable nominee is refused" as **system behavior**. The **cadence and selection heuristic** (which viable goal, how ranked, *when* to propose) are **deliberately unspecified** (PRD §5.5; story note) — the caller's judgment, recorded in the brain as the Proposal element (§7.1: the selection judgment lives in the brain, not a scheduler-side log). In v1 there is no autonomous scheduler: `make-proposal` is invoked by the conversational agent (loopback) — the *simplest honest mechanism*; the server guarantees the **contract**, not the choice.
6. **`POST /api/normalize/make-proposal`** (the `proposed` producer; agent/owner-invoked, **no UI trigger**; in `normalize/index.js` beside the goal-write primitives, registered in `registerNormalizeRoutes`). Gate first (`if (!isOwner(req) && !req.localTrusted) return 403`). Body `{goal, whyNow, passedOver?:[{goal, whyNot}]}`. Validation **before any write**: 400 for missing/empty `goal`/`whyNow`; each `passedOver` entry must carry non-empty `goal` + `whyNot` (refusal `runner-up-incomplete`); refusal `too-many-runners-up` if `passedOver.length > MAX_PASSED_OVER` (d15). Then, inside **one** `serializeGoalWrite` task: resolve goals (`resolveGoalConcept` + `fetchGoalRecords` + `resolveDecomposition`); the nominee must be a **viable leaf** (`goal-not-found`/`ambiguous-slug`/`not-viable`); each `passedOver` goal must resolve, be a **viable leaf**, and be **distinct** from the nominee and from the other runners-up (`runner-up-unknown`/`runner-up-not-viable`/`runner-up-is-nominee`/`runner-up-duplicate`); the nominee must have **no open proposal** (`already-open` — d11's open-derivation); then `ensureProposalConcept()` (d8); mint the append-only `proposed` element `{type:'proposed', goal, whyNow, passedOver, summary:whyNow, happenedOn:today}`. Result `{success:true, result:'proposed', proposal:{slug, goal}}`. Refusals loud, named, HTTP-200 `{success:false, refusal, error}`, nothing written past the point of failure.
7. **`POST /api/normalize/approve-proposal` and `POST /api/normalize/skip-proposal`** (the decision producers; the Proposal-queue UI card buttons invoke these — the first owner-facing brain UI writes; also loopback-callable). Both gate first, then a **shared `decideProposal({proposalId, decision, reason})` core** run inside **one** `serializeGoalWrite` task: read proposals; find the `proposed` element whose `slug === proposalId` (refusal `proposal-not-found`); refuse **`already-decided`** if any decision already references it (the **decided-exactly-once** guard — safe under the mutex against a double-click); for **skip**, the handler validates a **required non-empty `reason`** *before* the core (400/`reason-required` — AC4's server enforcement of "disabled until non-empty"); mint the decision element `{type:decision, proposalId, goal:<nominee slug from the proposed element>, reason?, summary:(decision==='skipped' ? reason : the proposed element's whyNow), happenedOn:today}`. Result `{success:true, result:decision, decision:{proposalId, goal, type}}`. `approve` carries no reason. **Neither handler launches anything** — they write facts only; no code path spawns a session, enqueues, schedules, or calls out (the v1 launcher is the owner; §7.3/AC3).
8. **Self-bootstrap `ensureProposalConcept()`** (module-internal, idempotent) — a structural copy of `ensureWorkRecordConcept` (ADR 0005 d8): resolve the Proposal header; if present, return (so `save-schema` — which re-signs the schema node — runs only when **absent**; no per-write churn). If absent: `create-concept` (name `tapestry proposal`, a plain description) treating "already exists" as success; `save-schema` with the complete d1 schema (the d8 fold reconciles the primary property in the same call); re-resolve. Runs inside the write path's `serializeGoalWrite` + owner/loopback gate, via `invokeNormalizeHandler`. **Never firmware-seeded** (§7.8); the first-run bootstrap is journaled at implementation with the complete schema JSON. Self-provisions **per instance on first `make-proposal`** (staging/prod gain it on their first live proposal).
9. **Serialization.** All three producers run their read-validate-write bodies (including `ensureProposalConcept`) through the **existing** `serializeGoalWrite` — **not renamed** (story-3 S5 / story-4 S4 / story-5 pins). `mintProposalElement` holds no mutex, and no producer composes another serialized core (unlike `createWorkRecord` composing `createResource`), so there is **no nested-mutex deadlock**. One process-singleton queue serializes all brain mutations, so a proposal write never interleaves a read-validate-write race with a concurrent goal/resource/record write — this is what makes the `already-open` and `already-decided` guards correct under concurrency.
10. **Read surface — the `records` array gains the proposal projection; the brain module's eighth require.**
    - **New pure core `src/lib/brain/proposals.js`** (d-free CJS, the `work-records.js` precedent): `parseProposalRow(row)` (whitelisting parser → `{uuid, name, slug, summary, type, goal, whyNow, passedOver, proposalId, reason, happenedOn, createdAt}`; non-proposal/malformed rows → `null`, never throws), `groupProposalsByGoal(records)` → `Map<goalSlug, record[]>`, **`openProposals(records)`** (partition by `type`; a `proposed` is **open** iff no `approved`/`skipped` record has a matching `proposalId`; returns the open `proposed` records, newest `happenedOn` first — the queue's pure logic), a `proposalEntry(record)` projection → `{date: record.happenedOn, type: record.type, summary: record.summary}` (the goal-detail spine shape; `summary` is uniform across types — d1), and `PROPOSAL_TYPES`. **Pure and dependency-free** (the zero-require assertion).
    - **`handleGetGoalDetail`** (`src/api/brain/index.js`): a new `readProposals(taPubkey)` helper (EXPLICIT ∪ IMPLICIT on `39998:<TA>:tapestry-proposal`, tolerant of the concept's absence — a fresh instance answers `[]`, reusing the module's `EXPLICIT_CYPHER`/`IMPLICIT_CYPHER`); group by goal; project the winning goal's proposal facts via `proposalEntry` to `{date, type, summary, session:null, questions:[], produced:[]}`; **merge** with the work-record entries and re-sort the combined array **newest-`date` first** (a shared comparator; ties broken deterministically). The array stays the story-5 shape — `RecordEntry` renders proposal entries unchanged (recon).
    - The brain module gains **exactly one require** — `require('../../lib/brain/proposals')` — the **eighth** spec. It stays **read-only** (no mutation/strfry tokens). This trips the quintuple-pinned import surface → a **planned positive re-pin of all five sibling allowlists in this same diff** (d-Test guidance).
11. **`GET /api/brain/proposals`** (the queue read; the AC2 data surface; new brain read). Gate `isOwner(req)||req.localTrusted → 403`. Read all proposals (`readProposals`) + goals (`readResolvedGoals`); `openProposals(all)` (pure core); project each open `proposed` to a card `{proposalId: p.slug, goal: p.goal, goalName: <name from the goals read, fallback slug>, whyNow: p.whyNow, passedOver: (p.passedOver||[]).map(x => ({goal:x.goal, goalName:<name|slug>, whyNot:x.whyNot})), madeOn: p.happenedOn}`; sort newest `madeOn` first. Empty → `{success:true, proposals:[]}` (the UI renders the canonical empty state — an empty queue is a state, not an error). No `orient`-style cap is needed (open proposals are bounded by the viable-goal count, at most one open per goal — d6's `already-open`). The read performs **no egress**; it is consumed by the owner UI (and is loopback-readable).
12. **Proposal-queue UI (the third v1 view) — new page + hook + route + nav; GoalDetail unchanged.**
    - **`ui/src/pages/brain/Proposals.jsx`** (new) — mirrors `Goals.jsx`: owner gate via `useAuth`; loading skeleton; error with the accessible `.brain-retry` `<button>` + `refetch`; the canonical **empty state** verbatim: *"No proposal right now — the next one appears when there are viable goals to choose between."*; the **error** state verbatim: *"The proposer couldn't run — its last message: {plain-English reason}. Nothing was decided for you."* Page title **"What next?"** (wireframes §3). ## Consequences

- **Enables:** the propose/decide loop end-to-end — the system nominates exactly one viable goal (server-verified) with a why-now and named runners-up; the owner approves (launching nothing in v1) or skips with a required reason; every decision is a dated, append-only fact on the nominated goal's one spine; the queue shows only open proposals; nothing is decided silently. The `records` array now carries all five design-guide type words. The accumulated `approved`/`skipped` decisions are the **calibration corpus** the Phase-2→3 entry metric counts (agreement ≥50% over ≥15 decisions — PRD §10); the decision record's completeness is structurally guaranteed (append-only, one spine).
- **Constrains:** the goal↔proposal and proposal↔decision linkages are **record-based** — any future edge materialization must supersede this ADR **and** go through the relationship-primitives whitelist path; proposals and decisions are **append-only with no edit/verify/delete** (a re-open/retract flow, if ever wanted, is a new append, not a mutation); one **open** proposal per goal at a time (d6 `already-open`); a proposal nominates one goal; the brain module stays read-only (proposal **writes** live in normalize). The queue/detail server reads reuse the O(N) `readResolvedGoals` + a full proposal scan — a sub-linear index is Phase 4, out of scope.
- **Debt / follow-ups:** (a) Proposal is **not yet covered by the hygiene check** (`HYGIENE_CONCEPTS` unchanged) — a dangling-`goal`/dangling-`proposalId` classifier is a natural later addition; the read path is already tolerant. (b) The raw `save-element-json`/`set-json-tag` hatches can still write unvalidated proposal fields — pre-existing flagged debt, compensated by read-time tolerance. (c) **Proposal auto-expiry / queue-age is Phase 2** (PRD §8.3) — deliberately not built; an open proposal stays open until the owner decides it. (d) The `make-proposal` **selection heuristic** is the caller's (unspecified) — a brain-side selection engine is Phase 2/3. (e) The approve confirmation copy is a ratification gate (d16). (f) `MAX_PASSED_OVER` is a legibility bound, not a PRD requirement — the operator may adjust it.
- **Firmware reinstall required? No.** The concept is runtime-created (self-bootstrapped); the installer is untouched; the d8 fold's install-time reach is unchanged from ADR 0004/0005.

## Out of scope

- **The proposer's cadence / scheduler / automatic triggering** and any **brain-side selection engine** — **Phase 2/3** (PRD §8.3). `make-proposal` is invoked by the gated caller in v1; the server validates + records, it does not choose.
- **Proposal auto-expiry / queue-age metric** — **Phase 2**; an open proposal stays open until the owner decides it.
- **Autonomous launch / the brain-side "launch answer" / claim-lease / scheduler write-back** — **Phase 2/3**; approve records a decision, the owner launches in v1.
- **Priority-signal consumption** (a why-now citing recorded signals) — **story 7**; story 6 does not read or depend on signals.
- **Editing / deleting / retracting / re-opening a proposal or decision** — append-only; corrections are new facts (§7.2).
- **A second open proposal for the same goal; proposing a goal with children / a non-viable goal** — refused (`already-open` / `not-viable`).
- **The morning-review digest / cross-goal roll-up** — **Phase 3**.
- **A mechanism-enforced private mode; hygiene coverage of the Proposal concept; any firmware/installer change; gating `save-element-json`/`set-json-tag`** (pre-existing debt); **a sub-linear server-side index** (Phase 4); `PUBLIC_MUTATIONS`/middleware changes.
